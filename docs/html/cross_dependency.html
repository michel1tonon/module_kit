CrossDependency<RETURN, PARAM>

Simple contract for module-to-module communication without importing internals.

Convention, not a requirement. This class exists to establish a common pattern and to remind engineers that cross-module integration can be modeled through explicit boundaries. It is optional: if a local interface or abstract class in your codebase serves the same purpose, use that instead.

Why It Matters

  • Encourages self-contained modules.
  • Avoids direct feature coupling.
  • Eases evolution to multi-package architecture.

Architectural View

  • Treat CrossDependency as a boundary port between modules.
  • All contracts belong in src/shared, not inside feature internals — this keeps them visible to the entire project.
  • The owner feature provides the adapter/implementation.
  • Consumer features depend only on the contract, preserving dependency direction.
  • This keeps modules replaceable, testable, and ready for micro frontend evolution.

Practical Contract + Implementation

// src/shared/cross/select_country_cross.dart
abstract class SelectCountryCross
    implements CrossDependency<Future<String?>, SelectCountryInput> {}

// features/select_country/cross/select_country_cross_impl.dart
class SelectCountryCrossImpl implements SelectCountryCross {
  @override
  Future<String?> call(SelectCountryInput param) async {
    // owner module flow
    return 'BR';
  }
}

Recommended Boundary

  • Keep every contract in src/shared so all modules can import it.
  • Keep implementation in the owner feature module.
  • Consumers should depend on the contract, not concrete internals.

What It Does Not Solve

Cyclic dependencies. CrossDependency defines a communication boundary — it does not break dependency cycles between features. If two modules need each other, that tension must be resolved at the Application (app shell) level: compose modules, wire implementations, and orchestrate flows there — not by letting features depend on one another directly.
